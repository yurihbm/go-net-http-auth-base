# Authentication and Email Flows

Reference for the sign-up, OAuth, session, step-up and email change behaviour. Error keys are listed in [ERRORS.md](ERRORS.md), audit actions in [AUDIT.md](AUDIT.md), and the decisions in [ADR-005](adr/ADR-005-security-approach.md), [ADR-007](adr/ADR-007-step-up-and-email-change.md), [ADR-008](adr/ADR-008-otp-email-proof-and-verified-accounts.md) and [ADR-009](adr/ADR-009-per-address-code-failure-counter.md).

## Email Provider

`domain.EmailProvider` (`Send`) is built once in `factories.Dependencies`: `ResendEmailProvider` when `RESEND_API_KEY` is set, otherwise `LogEmailProvider` (development). `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_CHANGE_REVERT_URL` and `EMAIL_OAUTH_LINK_REVERT_URL` are required outside development; all are loaded and validated in `config/config.go`. `LogEmailProvider` logs the plain-text body (codes and undo links) so flows can be tested locally, except when `API_ENV` is `production`, where it logs only the recipient and subject (the undo link carries a JWT). The Resend adapter retries failed API calls (transport errors, 429, 5xx and a concurrent-idempotency 409; up to 3 attempts within 15s, with a per-send `Idempotency-Key`), but a notice whose send failure is only logged can still be lost when every attempt fails (ADR-010).

## Email Normalization

Services always pass emails through the unexported `normalizeEmail` helper (`services/helpers.go`, trim + lowercase) before lookup or write; repositories receive already normalized emails; the database enforces a unique index on `lower(email)`.

## Sign-Up (Email Proof)

Every account is verified: it only exists after its email was proven with a 6-digit code typed in the browser that started the flow, never a link, so there is no `email_verified` column (ADR-008).

`domain.EmailVerificationService` (`services.NewEmailVerificationService`, depends only on `TokenService`, `EmailProvider`, `EMAIL_CHANGE_REVERT_URL` and `EMAIL_OAUTH_LINK_REVERT_URL`) builds and sends the emails (`SendSignupCode`, `SendOAuthSignupCode`, `SendStepUpCode`, `SendEmailChangeCode` and the undo notices `SendEmailChangedNotice` and `SendOAuthLinkedNotice`). `domain.PendingSignupService` (`services.NewPendingSignupService`: `PendingSignupRepository`, `EmailSendLimiter`, `UsersRepository`, `Transactor`, `EmailVerificationService` and the `JWT_SECRET` HMAC key) only stores, codes, limits and mails.

`StartCredentials` backs `POST /users` (`202 users.create.pending`, no user body): it normalizes the email, rejects a taken or reserved one early with `409 users.email.conflict`, reserves a send before hashing so a refused request costs no CPU (`EmailSendLimiter.ReserveSend`: 60s cooldown and 5 per hour per address, `429 auth.email.sendLimit`, the slot is never refunded, not even when hashing fails), hashes the password with bcrypt (outside any transaction), inserts a `pending_signups` row (UUIDv7 generated in the service, since the code hash needs it before the insert; code stored as `HMAC-SHA256(JWT_SECRET, "signup:<uuid>:" + code)`, valid 10m with 5 attempts; the sign-up lives 1h from creation and is never extended; several rows per email may coexist and the first correct code wins) and mails the code; a send failure deletes the row and is `500 auth.signup.sendFailed`. `StartOAuth` does the same for kind `oauth` (provider and provider user ID, no password, no early conflict check); `AuthService.OAuthLogin` calls it, outside any transaction, when the provider email is not verified (see below). The handler sets the HttpOnly `pending_signup` cookie (`api.SetPendingSignupCookie`: `__Host-` prefix outside development, path `/`, `SameSite=Strict`, 1h).

`Resend` backs `POST /auth/signup/resend` (`202 auth.signup.codeResent`): it replaces the code and resets the attempts in one `WithinTx` with the send reservation, so a refused send keeps the old code (the per-address 60s cooldown of `ReserveSend` also limits resends, `429 auth.email.sendLimit`); a failed send is `500 auth.signup.sendFailed` and keeps the row (the new code already replaced the old one, so the user resends after the cooldown); only a send failing right after the row was created deletes it.

`Attempt` loads the sign-up, reserves a guess for the address (`EmailSendLimiter.ReserveCodeGuess`, one atomic upsert on `email_send_limits.failures` that only increments below 20 and restarts the 24h window, else `429 auth.email.codeLocked`, so parallel guesses can never exceed the cap; the counter is per address only, so an anonymous attacker can lock a victim's verification for up to 24h per lockout and renew it by repeating the attack, an accepted residual risk, see [ADR-009](adr/ADR-009-per-address-code-failure-counter.md)), counts the attempt in its own statement (`PendingSignupRepository.Attempt`, a missing, expired or exhausted sign-up refunds the guess) and compares with `hmac.Equal`; a match gives the guess back (`EmailSendLimiter.RefundCodeGuess`, a failure is only logged), a mismatch keeps it and is `401 auth.signup.invalidCode`; missing, malformed, expired or exhausted sign-ups are all `401 auth.signup.noPending`. `Consume` deletes the row by UUID and code hash (`DELETE ... RETURNING`, single use, wins a double submit).

`AuthService.CompleteSignup` orchestrates the public `POST /auth/signup/verify` (needs the cookie, else `401 auth.signup.noPending`; body `CodeDTO`): `Attempt` outside any transaction, so wrong codes are never rolled back, then one `WithinTx` with `Consume`, `UsersService.Create` (`NewUserDTO` with the already hashed password, reservation check inside the transaction) and `startSession`; a conflict rolls back and keeps the sign-up. For kind `oauth` the same transaction resolves the account with `findOrCreateOAuthUser` treating the email as verified (the code proved the mailbox): an existing link for the provider user signs in to that user, else the user that owns the email gets the provider linked, else `UsersService.CreateOAuth` creates the user (reservation check inside) and the provider is linked. A `409` in an OAuth completion may come from a concurrent link or create, so `CompleteSignup` retries the whole `WithinTx` once (the rollback restored the pending row, so `Consume` succeeds again; `Attempt` is not repeated), where the winner's records are found; credentials conflicts are not retried. The handler answers `201 auth.signup.success` with the user, sets the auth cookies (`api.SetAuthCookies`), deletes the pending cookie and logs `USER_CREATE`.

## OAuth Login

OAuth login with a provider-verified email creates the account or links into the one that owns it right away, and a provider link that already exists always signs in. `AuthService.OAuthLogin` is one service method: it verifies the state token, resolves/creates the user via `UsersService`, links the OAuth provider, and mints tokens.

When the provider email is not verified (GitHub unverified primary, Microsoft) and no link exists, `findOrCreateOAuthUser` returns the unexported `errOAuthEmailUnverified` without writing, and `OAuthLogin` returns a result with `PendingSignupUUID` and no tokens after `StartOAuth` mailed the code to the provider email (`SendOAuthSignupCode`, which says that entering it signs in and links that provider account to the account for the email, so the owner of an existing account is not misled into sharing it; `Resend` picks the same email by kind) (`VerificationLimited` instead when the address hit the send limit, a `429`). The callback then sets the `pending_signup` cookie, clears the OAuth flow cookies, logs `SIGNUP_REQUEST` (provider in `changes`) and redirects (`302`) to the state's `redirect_uri` with `verification=required` added to its query (existing params are kept); the frontend shows the code form and posts `POST /auth/signup/verify` with credentials included, which signs the user in. With `VerificationLimited` it redirects with `error=verification_limited` and sets no cookie.

**Callback failures.** A provider `error` redirects to the state's `redirect_uri` with `error=<code>` (`access_denied` unless the provider sent a standard code). When `OAuthLogin` fails, the controller logs `OAUTH_LOGIN` (failure), then verifies the state and the browser nonce again: if both verify and the `redirect_uri` is in `OAUTH_CALLBACK_ALLOW_LIST` it clears the flow cookies and redirects with `error=<code>` (`missing_code_verifier`, `account_conflict` for any `ConflictError`, `invalid_user_info`, `server_error` for everything else); otherwise (invalid or expired state, provider or nonce mismatch, `redirect_uri` not allowed) no trusted redirect exists and the error is answered as JSON by `HandleError`.

**Link notice and undo.** A provider-verified email that matches an existing account (Case 2 of `findOrCreateOAuthUser`) links the provider silently for the user, so the owner is told: `OAuthLogin` sends `SendOAuthLinkedNotice` to the account email after the link transaction committed and after `startSession`, outside any transaction (a failure is only logged, the login still succeeds; ADR-010 residual risk; if the session cannot start the notice is still sent, because the link is persisted). The notice goes to the provider-asserted address, so it protects against a provider wrongly asserting verification, not against a recycled mailbox, and the undo does not block the same login from linking again (ADR-011). `findOrCreateOAuthUser` returns the created link only in Case 2, so an existing link (Case 1), a new user (Case 3), the unverified path and `CompleteSignup` (the code email already told the owner that entering it links the provider) send nothing. The link carries a JWT with audience `oauth_link_revert_token` (72h, subject the user, payload `link_uuid` of the `user_oauth_providers` row and `provider`) and points to `EMAIL_OAUTH_LINK_REVERT_URL`. `AuthService.RevertOAuthLink` backs the public `POST /auth/oauth/revert-link` (body `RevertOAuthLinkDTO` `{token}`): in one `WithinTx` it deletes the link of that user (`AuthRepository.DeleteUserOAuthProviderOfUser`, `DELETE ... WHERE uuid AND user_uuid`) and all the user's sessions (`SessionsRepository.DeleteAllByUser`); no row deleted (already undone or removed) is `401 auth.oauthLink.staleToken`, which is what makes the token single use without stored state; a bad token is `401 auth.invalidToken`. The handler logs `OAUTH_LINK_REVERT`, clears the auth cookies and answers `200 auth.oauthLink.reverted`. The access token of a revoked session stays valid up to 15 minutes (stateless `AuthMiddleware`). See ADR-011.

The Microsoft provider (`common` endpoint, scopes `openid email profile`, identity from Graph `/oidc/userinfo`, keyed by its `sub`, which is pairwise per app registration) always reports `EmailVerified=false`, because the Entra email is mutable and tenant-controlled (nOAuth), so a first Microsoft login always proves the email by code.

## Refresh Sessions

Multi-device: each login (credentials or OAuth, via `startSession`) creates a row in `user_sessions` (`current_jti`, `last_used_at`, `expires_at` = login + `SESSION_MAX_AGE`, never extended on rotation), inside one `WithinTx` that first deletes the user's expired or idle sessions and then trims the user to the newest `MAX_SESSIONS_PER_USER` (optional, default 10; least recently used evicted). Refresh tokens carry `sub`, `sid` and `jti`; access tokens carry `sub` and `sid` (`tokenService` rejects either without `sid`).

Refresh loads the session by `sid` + `sub`, rejects it past `expires_at`, and rotates the `jti` through `SessionsRepository.RotateJTI` (per-session atomic compare-and-set, keeping the same `sid`); a reused or stale token, or a lost concurrent refresh, deletes only that session (the user's other devices stay signed in). There is no grace window, so clients must send one refresh at a time. Confirming or reverting an email change deletes every session of the user.

`infra.ExpiredRecordsSweeper` (startup, then hourly) also deletes expired or idle sessions of all users, expired session challenges (step-up and email change), expired pending sign-ups, expired password resets and `email_send_limits` rows whose send and failure windows both ended, in batches of 1000, so rows of users who never log in again do not linger.

`POST /auth/logout` is authenticated (`AuthMiddleware` puts `SessionUUID` in `shared.RequestContextData`) and deletes only the current session; the stateless access token stays valid for up to 15 minutes after logout, but the session can no longer be refreshed. With an expired access token, clients refresh first and then log out. `POST /auth/logout-others` (`AuthService.LogoutOthers`, authenticated, `204`) deletes every other session of the user through `SessionsRepository.DeleteOthersByUser`, after checking the current session still exists and is not expired (`401` otherwise, so a revoked session cannot wipe the owner's new ones). Deleting your own account (`DELETE /users/{uuid}` with the caller's UUID) also clears both auth cookies, like logout; the sessions go with the user row, and deleting another user leaves the caller's cookies alone.

## Step-Up

Sensitive routes (`POST /users/me/email`, `POST /users/me/password`, `DELETE /users/{uuid}` including admins) need an OTP sent to the user's current email. `domain.StepUpService` (`services.NewStepUpService`):

- `RequestCode` (`POST /auth/step-up`, `202`) checks the session is live, generates a 6-digit code with `crypto/rand`, stores `HMAC-SHA256(JWT_SECRET, "step-up:"+sid:code)` as the session's `step_up` row in `session_challenges` (`SessionChallengeRepository.Upsert`: 10m TTL, `429 auth.stepUp.cooldown` within 60s per session; the table holds one row per session and purpose, `step_up` or `email_change`, with `new_email`/`email_version` only on email change rows, enforced by a CHECK, and cascades with the session and the user) and mails it with `EmailVerificationService.SendStepUpCode` (a send failure deletes the challenge so the cooldown does not trap the user, and is a `500`).
- `VerifyCode` (`POST /auth/step-up/verify`, body `CodeDTO`) counts the attempt first (`SessionChallengeRepository.Attempt`, max 5; missing, expired or exhausted challenges are all `401 auth.stepUp.noChallenge`), compares with `hmac.Equal` and, in one `WithinTx`, deletes the challenge and sets `user_sessions.step_up_until` to now + 5m; it returns `{ "step_up_until": <unix> }`.

`StepUpMiddleware` (depends on `domain.StepUpChecker`, runs inside `AuthMiddleware`, wired as `authMiddleware.Use(stepUpMiddleware.Use(handler))`) loads the session through `IsElevated` and answers `403 auth.stepUp.required` when it is not elevated. `AuthMiddleware` stays stateless, so only sensitive routes read the session row.

`user_sessions.step_up_failures` counts every wrong code of the session (`SessionsRepository.IncrementStepUpFailures`, never reset by new codes or successful verifications); at `StepUpMaxSessionFailures` (10) the session is deleted and `VerifyCode` returns `401 auth.stepUp.sessionRevoked`, and the controller clears the auth cookies. `users.step_up_failures` and `step_up_failures_window_start` add a per-user cap across sessions: `VerifyCode` first reserves a guess (`UsersRepository.ReserveStepUpGuess`, one conditional UPDATE that increments only below `StepUpMaxUserFailures` (20) and restarts the count when the 24h window expired; no row is `429 auth.stepUp.userLocked`), so parallel guesses across sessions cannot pass the cap, and refunds it (`RefundStepUpGuess`, failure only logged) on a correct code or a failed attempt; `RequestCode` also answers `429 auth.stepUp.userLocked` while the cap is reached, until the window ends. See ADR-007.

## Email Change

`PUT /users/{uuid}` never changes the email (`UserUpdateDTO` has only `name`). The flow lives in `EmailChangeService` (`services/email_change_service.go`), separate from `UsersService`; both share the `ensureEmailNotReserved` and `isEmailChangeLocked` helpers.

**Request.** `EmailChangeService.RequestEmailChange` backs `POST /users/me/email` (self only, behind step-up; `409` if taken, reserved or `users.emailChange.locked`). In one `WithinTx` it upserts the session's `email_change` row in `session_challenges` (`SessionChallengeRepository.Upsert`: `new_email`, the user's `email_version`, `HMAC-SHA256(JWT_SECRET, "email-change:"+sid:code)`, 10m TTL, one row per session, a new request replaces it, `429 users.emailChange.cooldown` within 60s) and reserves a send for the new address (`EmailSendLimiter.ReserveSend`, `429 auth.email.sendLimit`), then mails the 6-digit code to the new address with `EmailVerificationService.SendEmailChangeCode` (a send failure deletes the challenge and is a `500 users.emailChange.sendFailed`).

**Confirm.** `ConfirmEmailChange` backs the authenticated `POST /users/me/email/confirm` (body `CodeDTO`, not behind step-up because the requesting session already passed it): it reads the session's challenge to learn the new address (`SessionChallengeRepository.Find`; no challenge for this session or an expired one is `401 users.emailChange.noChallenge`, so another device cannot confirm), reserves a guess for that address (`EmailSendLimiter.ReserveCodeGuess`, shared with sign-up through the unexported `guessCode` helper, `429 auth.email.codeLocked` at 20 wrong codes in 24h), counts the attempt in its own statement (`SessionChallengeRepository.Attempt`, max 5; an exhausted or expired challenge, or one replaced for another address, refunds the guess and is `401 users.emailChange.noChallenge`), compares with `hmac.Equal` (a mismatch keeps the guess and is `401 users.emailChange.invalidCode`; a match refunds it with `RefundCodeGuess`, a failure is only logged), rejects with `users.emailChange.staleToken` unless the account `email_version` equals the challenge's (also blocks A to B to A replays) and with `users.emailChange.locked` for 72h after the last change (`domain.EmailChangeLock`), then in one `WithinTx` writes the email and stamps `email_changed_at` (`UsersRepository.UpdateEmail`, compare-and-set on the version) and deletes all the user's sessions (`SessionsRepository.DeleteAllByUser`, the challenge goes by cascade); the handler also clears the auth cookies.

**Undo.** After commit it notifies the old address with an undo link (`SendEmailChangedNotice`, failure only logged). The link carries a JWT with audience `email_change_revert_token` (72h, payload `old_email`/`new_email`/`ver` after the change/`changed_at`) and points to `EMAIL_CHANGE_REVERT_URL`. `RevertEmailChange` backs the public `POST /users/revert-email-change`: it requires the account to still have `new_email` at version `ver` (single use, because the revert bumps the version; the lock prevents chained changes), then in one `WithinTx` restores `old_email` (clearing `email_changed_at` so the owner is not locked), deletes all sessions and deletes the OAuth providers linked since `changed_at` (`AuthRepository.DeleteOAuthProvidersCreatedSince`); the handler clears the auth cookies.

**Reservation and lock.** During the lock the previous email stays reserved: `UsersRepository.UpdateEmail` stores it in `users.previous_email` (cleared by a revert), and `UsersRepository.IsEmailReserved` (case-insensitive, only while `email_changed_at` is inside the lock window) makes `Create`, `CreateOAuth`, `RequestEmailChange` and `ConfirmEmailChange` reject that address with `users.email.conflict` (`Create`, `CreateOAuth` and the confirm check after their write inside a `WithinTx`, so a write that waited on a concurrent confirm sees its reservation and rolls back; bcrypt stays outside the transaction), the same key as a taken email; the revert itself is unaffected. `UsersService.Delete` returns `409 users.emailChange.locked` when the actor deletes their own account during the lock (an admin deleting another user is unaffected).

See ADR-007.

## Password Reset and Change

`PasswordService` (`services/password_service.go`) backs three routes. Accounts without a password (OAuth only) may use reset to set a first one and change to replace it. See [ADR-014](adr/ADR-014-password-reset-and-change.md).

**Request.** `POST /auth/password/forgot` (public, body `ForgotPasswordDTO`) always answers `202 auth.passwordReset.requested` and sets the HttpOnly `password_reset` cookie (`api.SetPasswordResetCookie`: `__Host-` prefix outside development, path `/`, `SameSite=Strict`, 10m). Order for every address: normalize the email, reserve a send (`EmailSendLimiter.ReserveSend`, the same 60s cooldown and 5 per hour as sign-up, so an unknown address is `429 auth.email.sendLimit` too and the slot is never refunded), then look the user up. A known address gets a `password_resets` row (UUIDv7 generated in the service, `user_uuid`, `email`, the user's current `email_version`, `HMAC-SHA256(JWT_SECRET, "password-reset:<uuid>:" + code)`, 0 attempts, 10m expiry) and the 6-digit code by email (`SendPasswordResetCode`, synchronous; a send failure deletes the row and is `500 auth.passwordReset.sendFailed`). An unknown address gets a fresh UUIDv7 in the cookie with no row and no email. The response timing can still tell the two apart (accepted, consistent with `POST /users` answering `409` for taken emails).

**Reset.** `POST /auth/password/reset` (public, body `ResetPasswordDTO`: `code` and `password` `min=8,max=64,maxbytes=72`) reads the cookie. `ResetPassword` loads the row, counts the guess outside any transaction exactly like sign-up (`guessCode`: `ReserveCodeGuess` per row email, `PasswordResetRepository.Attempt` with 5 attempts per row, `RefundCodeGuess` on a match; a locked address is `429 auth.email.codeLocked`, ADR-009), hashes the password with bcrypt outside the transaction, then in one `WithinTx`: `Consume` (`DELETE ... RETURNING` by UUID, code hash and expiry), `UsersRepository.UpdatePassword` with compare-and-set on `users.email_version` (an email change since the request makes the reset stale), `SessionsRepository.DeleteAllByUser` and `PasswordResetRepository.DeleteByUser`. After the commit it mails a notice (`SendPasswordChangedNotice`, failure only logged). The handler answers `200 auth.passwordReset.success`, clears the reset cookie and the auth cookies, and does not log in. A missing cookie, unknown, expired or exhausted row, wrong code and stale version are all `401 auth.passwordReset.invalidCode`.

**Change.** `POST /users/me/password` (body `ChangePasswordDTO`: `new_password` `min=8,max=64,maxbytes=72`) is behind `authMiddleware.Use(stepUpMiddleware.Use(...))` and does not ask for the current password: the step-up proves the mailbox. After bcrypt (outside the transaction), one `WithinTx` runs `UpdatePassword` (no version check), `SessionsRepository.DeleteOthersByUser` (keeps the current session) and `PasswordResetRepository.DeleteByUser`, then the notice is sent (failure only logged). The answer is `204`.

Access tokens already issued stay valid until they expire (15 minutes), as with every session revocation.

## Optional Authentication

Decided in [ADR-017](adr/ADR-017-feature-flags.md). `OptionalAuthMiddleware` serves routes that answer both anonymous and signed-in callers (`GET /feature-flags/enabled`). A request without the `access_token` cookie continues as anonymous: `shared.RequestContextData` keeps an empty `UserUUID`. When the cookie is present it goes through `AuthMiddleware` unchanged, so an invalid or expired token is `401 auth.unauthorized` instead of anonymous, and the client refreshes the session and retries. Routes that need a session keep using `AuthMiddleware`.

## HTTP Edge

Decided in [ADR-015](adr/ADR-015-http-edge-hardening.md). `SecurityHeadersMiddleware` sets `X-Content-Type-Options`, `Cache-Control: no-store`, `Referrer-Policy`, a deny-all CSP and, outside development, HSTS on every response, including 429 and panic 500s; only Swagger UI routes override the CSP. Besides the global per-IP limiter, `POST /auth/login`, `POST /users`, `POST /auth/signup/verify`, `POST /auth/signup/resend`, `POST /auth/password/forgot`, `POST /auth/password/reset`, `POST /users/revert-email-change`, `POST /auth/oauth/revert-link`, `POST /auth/step-up` and `POST /auth/step-up/verify` sit behind a stricter per-IP bucket (`RATE_LIMIT_CREDENTIALS_PER_MINUTE`, `RATE_LIMIT_CREDENTIALS_BURST`), applied before the auth and step-up middlewares and answering the same `429 rateLimit.exceeded`. Refresh, logout and the OAuth login and callback are not covered. Both limiters key IPv6 clients by /64. Every response carries `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset`, and a `429` also carries `Retry-After` (whole seconds until a token is available); CORS exposes all four so browser clients can read them.

## Token Interfaces

All JWTs are signed and verified by the dependency-free `tokenService` (`services.NewTokenService`, holds only the JWT secret; `domain.TokenService`), used by `AuthService` (which delegates its token methods to it) and `EmailVerificationService`. `domain.TokenVerifier` (`VerifyToken`) is what middlewares depend on; `domain.TokenGenerator` (`GenerateToken`) is separate and not part of `AuthService`. Depend on the narrowest one.
